# PostgreSQL 17 + pgvector, end to end (verified 4 Nov 2026)

Closes handoff gap **G1**. Everything below was run on this machine (Windows 11, Docker Desktop 29.9.2,
Compose v5.6.1) and the outputs are quoted, not assumed. The older "PostgreSQL 16.2 + pgvector 0.6.2 via
pgserver" note in docs/00_STATUS.md was a historical check of an earlier version; this document is the
evidence for the CURRENT code.

## Real bugs this run found (all fixed, all with regression tests)

The docs said an earlier version had been verified on Postgres, but the current code had never run there. It failed immediately:

1. **`alembic upgrade head` crashed on a fresh database** - `DuplicateColumn: regions_json`. Migration 0001 builds the
   schema with `create_all()` from the *current* models, so 0002/0003 then tried to add columns that already existed.
   Fix: 0002/0003 are idempotent (add only if missing). New migration 0004 widens columns, 0005 adds `printed_label`.
2. **`classification_runs.provider` was `VARCHAR(20)`** but `auto` runs write `auto:gemini+openrouter` (22 chars) -
   SQLite ignores lengths, PostgreSQL does not, so the first real multi-provider run would have crashed. Widened
   (migration 0004); test `test_classification_run_accepts_composite_provider_and_model_values`.
3. **Exports were not deterministic**: several queries had no `ORDER BY`, so SQLite and Postgres produced the same rows
   in different order. All export/analytics queries are now ordered; all 7 CSV exports are byte-identical across backends.
4. **Test-suite hang**: Streamlit's `AppTest` script kept a session `idle in transaction`, and the next test's `TRUNCATE`
   waited forever. The fixture now terminates stray backends on the `*_test` database, and the app closes its previous
   session on every rerun (a long-lived Postgres-backed UI could otherwise pile up locked connections).
5. A test inserted rows that violate foreign keys (`Question` with no `Paper`, `AnswerKey` before its `Question`) - SQLite
   never enforced them. Fixed in the test.

The matrix check compares MARKS to paper totals; the drill-down check compares QUESTION COUNTS to cell counts (different
numbers, both verified). Real full-text search runs through `plainto_tsquery('english', ...)` over the generated column.

## Persistence

`docker compose restart postgres` -> `Up ... (healthy)`; re-running verify_postgres.py gave identical counts
(29 / 1885 / 65 / 0 / 3). The data lives in the named volume `gate_pgdata`.

## Backup and restore (drilled)

`python -m src.cli backup` on Postgres wrote a 391 KB custom-format dump (`pg_dump -Fc` run inside the container because
no local `pg_dump` exists). It was restored with `pg_restore` into a scratch database (`gate_restore_test`, since dropped):
**papers=29, questions=1885, review_events=3, GIN index ix_questions_fts present**. The live `gate_cse` was never touched.

## Not claimed

- pgvector is installed and enabled, but no embeddings exist yet (a later migration adds the vector column once a model is chosen).
- Performance at scale was not measured (1,885 questions is small).
